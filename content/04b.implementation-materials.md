# Applying the workflow to a research project

## Establish the project record and access boundary

Begin with a bounded, low-risk task using public or synthetic material. Identify the scientific objective, the background resources, the intended deliverable, and the evidence required for acceptance. Before connecting participants, determine which records and files each may access and where execution will occur. The workflow is not a validated protected-data solution. A project involving protected data requires an appropriate environment and a separately established data-handling boundary; the implementation instructions do not establish that those requirements have been met.

Create a Project Overview page, a structured Collaboration Log, and locations for versioned files and completed outputs. Add numbered notebooks for extended methods and analysis. The Overview identifies the accepted question, assumptions, current artifacts, unresolved limitations, and relevant prior work. A log entry records a material action and its next step rather than transcribing the entire conversation. The supplement provides the field schema, worked records, and a compact template for project-specific settings.

## Introduce the contract and Skill to each participant

Give each named session the same project-specific contract, the Overview, the log location, and a bounded assignment with explicit upstream references. Establish the project's `PRIOR-ART-LINEAGE` coverage declaration and maintain its search record separately from the citation ledger. The former records propositions, searches, and candidate dispositions; the latter records whether each source supports its assigned claim and how it was checked. `REFERENCE-VALIDATION` applies to references regardless of the declared search coverage.

The repository's `user-mediated-collaboration` Skill packages a `SKILL.md` instruction file with protocol, template, and Notion-setup references. It is an onboarding aid: it does not grant permissions, connect services, route work automatically, or certify that an instruction has been followed. The User still supplies the project locations and initiates each transition. The protocol can also be supplied as ordinary project instructions when a compatible Skill-loading mechanism is unavailable.

The current v0.1.0 package is a development artifact pinned to protocol snapshot `47ad152`. It predates some revisions in the current supplement and should not be treated as an interchangeable copy. Before use, compare the packaged snapshot with the project's adopted contract, resolve differences, and record which version governs. Neither packaging nor presence in the repository constitutes evaluation of Skill behavior or a formal release. The package is separate from the historical workflow characterized below.

## Run one task-review-acceptance cycle

A task record should state what must be done, why it is needed, which artifacts govern, who leads and reviews, what may not change, and what evidence will count as success. The operating cycle then proceeds through six stages.

| Stage | Action and durable output |
| --- | --- |
| Orient | The lead reads the assignment, adopted contract, current state, and named upstream dependencies. Missing context is identified before it is assumed. |
| Produce and record | The lead supplies the proposed code, analysis, text, or other artifact and logs its location, evidence, uncertainty, and next action. |
| Transfer, test, and version | The User inspects and transfers materials as needed, tests them in the appropriate environment, and versions the source. Completed external outputs receive recorded locations and checksums when appropriate. |
| Review | The reviewer inspects the actual artifact, assumptions, tests, execution evidence, and relevant sources rather than only the lead's summary. Objections and unverifiable points are recorded. |
| Resolve and accept | Required repairs and reruns are completed, or limitations are explicitly retained. The User applies the acceptance criteria and records the disposition. |
| Synchronize | The accepted revision, output location, run evidence, governing decisions, and next task are linked from the log and reflected in the Overview. |

The order of review and execution depends on risk. A reviewer can inspect a proposed script and test plan before execution, then inspect the resulting evidence afterward. A sandbox demonstration must not be relabeled as a completed final run. Repository write access is optional; in the dominant implementation, the User transferred files and controlled staging, commits, pushes, merge, and release. Any delegated write should have a defined scope and be recorded.

## Make review and verification explicit

Record what a reviewer inspected, what is supported, what remains uncertain, and which changes are required. The reviewer clears only their own outstanding review request after recording the response. Approval fields describe endorsement of a particular version, not votes that determine acceptance; material revision requires reconsidering prior approvals. Record session identity and whether the reviewer has already seen another participant's contribution when the action occurs. A second check following exposure is not independent confirmation.

After a record or artifact is written, fetch it again. Check location and retained properties separately. For transferred files, the receiving participant must be able to retrieve the actual artifact. A description of an output, an untested link, or a successful tool response does not establish that the intended shared state exists. The log should connect code, command, inputs, configuration, environment, and outputs sufficiently to check a reported result.

## Resume, redirect, and release

A handoff identifies accepted state, completed work, exact files and revisions, execution evidence including failed runs, unresolved questions, superseded work, and one next task with an owner and acceptance condition. The receiving session compares that handoff with the governing records before resuming. The aim is a task-relevant context set, not indiscriminate rereading of the whole project.

When a result changes the hypothesis or project direction, update the Overview, affected assumptions, dependencies, acceptance criteria, and assignments. A handoff that preserves an obsolete plan is not adequate simply because it is complete. Before release, reconcile the accepted source and outputs with their evidence and review records, complete the applicable citation and prior-art checks, and record unresolved limitations. Detailed release and troubleshooting procedures remain in Supplementary Note S1.

## Synthetic example: a pipeline revision

The supplement's synthetic pipeline example illustrates the cycle; it is not an additional observation from the study. Agent A implements a pipeline and tests it on a synthetic input. The log identifies the source revision, configuration, command, and output, and labels the result as sandbox evidence only. Agent B reviews the code, tests, and identifier handling and identifies defects requiring repair. The revised implementation is versioned, and the User performs the final run in the designated environment. Only after the resulting evidence meets the stated criteria is the accepted state updated. A subsequent session receives a handoff linking the accepted specification, revised source, run evidence, and remaining limitations rather than a claim that the analysis is simply "done."
