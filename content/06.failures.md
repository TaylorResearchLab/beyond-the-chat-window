## Operational failures and corrective practices

The following problems informed the implementation guidance. These are descriptive problem-control pairings, not estimates of failure prevalence or demonstrations that a control eliminated the problem. Controls evolved during use and subsequent manuscript development.

| Observed problem | Corrective practice carried into the guidance |
| --- | --- |
| A new session lacked the current project state | Link accepted-state pages and a structured handoff to the next assignment. |
| A confident statement had not been checked | Require artifact or source evidence against the acceptance criterion. |
| Agreement was mistaken for independent confirmation | State prior exposure and distinguish sequential agreement from independent checking. |
| The shared record and stored file no longer matched | Record the artifact location and exact repository revision together. |
| A material decision remained only in chat | Log the decision, its rationale, and its consequence for the next task. |
| A result lacked the code, input, or command needed to check it | Store or link supporting materials and outputs from the same record. |
| A Notion create or move appeared successful but produced the wrong state | Fetch the object and verify its location and retained properties separately. |
| Mutable review fields did not retain historical events | Freeze the analytical snapshot; for subsequent work, preserve dated reviews separately from current routing and approval fields. |

Freezing a snapshot preserves the state extracted; it cannot recover review events already lost from mutable fields. Likewise, later protocol additions cannot retrospectively supply model identities or exposure information that were not recorded at the time.
