# Retrospective evaluation

## Study design and corpus

This was a retrospective case study of one User coordinating GPT and Claude across several private workspaces that used the same Collaboration Log design. The analysis used a frozen snapshot defined by a fixed analytical cutoff established before extraction. The snapshot contained 728 records from seven standardized logs across six active workspaces. Freezing the snapshot defined the analytical corpus; it did not imply that the underlying projects were complete.

Logs with substantially different structures were retained for qualitative description but excluded from the total. The manuscript-development log was also excluded because it was created after the study boundary and is discussed separately as an additional case. No project-specific scientific findings are reported. To protect private work and collaborators, the paper describes collaboration functions rather than scientific domains or project-linked counts: code development and review, project-state management, literature retrieval and citation checking, analysis review, figure regeneration, independent recalculation, and consistency tracking for long-form writing.

The analysis used structured Collaboration Logs without synchronized exports of the underlying chats. It therefore did not estimate interaction-level routing rates, response times, or frequencies of agreement, disagreement, correction, and retraction. Tasks were assigned by the User rather than randomized or matched. The record was not designed to estimate comparative platform performance or synergy. The retrospective corpus characterizes the workflow's use, not the later Skill package or every provision of the current adoption materials.

## Implementation and access configuration

Routine coordination used paid ChatGPT Pro and Claude Pro interactive applications and a Notion Business workspace rather than model APIs. Both assistants could read and write the shared Notion record when prompted. Neither had direct access to the User-controlled computing environment. Repository access varied by platform and session. In most scientific projects, the User controlled file transfer, testing, staging, commits, pushes, pull requests, merge, and release. Connector-mediated repository writes were bounded exceptions, including parts of manuscript production, and were recorded because GitHub attributed them to the authenticated User.

Product plans, model identities, client builds, and connector versions were recorded separately. The following configurations describe the manuscript-development phase, not every action in the frozen corpus.

| Component | Manuscript-production configuration | Scope and limitation |
| --- | --- | --- |
| ChatGPT | Pro interactive application; GPT-5.6 Pro | GPT manuscript-development session reported in the study. Historical GPT model identity was not systematically recorded for each corpus record. |
| Claude | Pro interactive application; Claude Opus 5 (`claude-opus-5`) | Claude manuscript-development session reported in the study. Historical Claude model identity was not recoverable for each corpus record. |
| Notion interface | Business workspace; Version 7.30.0 (29d6ecb) | User-observed interface build during the manuscript phase. |
| GPT Notion integration | Remote Notion connector | Exact connector build and `Notion-Version` header were not exposed. |
| Claude Notion integration | Notion connector in Claude | Exact connector build and API-version header were not recorded or exposed. |

The corpus spans multiple model releases. Model selection could also change within a conversation, while platform routing was not independently observable. Historical records were not assigned to a specific model version unless it was explicitly documented at the time. Lower-cost plans and open-source implementations were not tested as equivalent conditions.

## Assessment of support for FAIR principles

The FAIR principles concern digital research objects rather than human-AI work processes [@doi:10.1038/sdata.2016.18]. The assessment therefore examined how documented workflow features and linked products supported FAIR-oriented practice. It did not assign a maturity score, certify compliance, or evaluate the private scientific datasets themselves.

The assessment covered standardized logs, notebooks, accepted-state pages, handoffs, repository and commit links, code and configuration records, run evidence, citation-validation records, and artifact locations. The manuscript-development record was considered separately from the frozen corpus. The criteria were searchable descriptions and stable identifiers for Findability; stated access conditions and actual retrieval by intended participants for Accessibility; repeated machine-readable fields and identifiers linking stores for operational Interoperability; and sufficient rationale, provenance, execution information, limitations, and review history for Reusability.

A feature counted as support only when the relevant record or linked object was documented and retrievable. Planned features were not evidence. Missing records, inaccessible links or files, incomplete execution information, invalid checksums, and tool limitations counted as incomplete support. Findings are reported as a descriptive matrix rather than a numerical score.
