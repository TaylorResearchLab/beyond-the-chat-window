# Workflow design

## Roles and authority

The human scientific lead, called the User, defines the question, scope, access boundary, acceptance criteria, and release decision. The User assigns work, evaluates evidence, resolves disagreements, and retains control of final execution and repository acceptance. AI participants propose, implement, test, review, challenge, and repair; they do not accept their own contributions into the governing project state. These responsibilities are defined in the work contract rather than negotiated separately in each conversation.

Two named sessions take task-dependent lead and review roles. The implementation studied used GPT and Claude, but the instructions use Agent A and Agent B to separate a role from a particular provider. Roles may reverse between work units. Coordination need not alternate evenly: one participant may complete several linked steps before another reviews the resulting artifact. A review therefore concerns a bounded work product, not an equal number of prompts or log entries.

## Shared state, versioned artifacts, and execution

The workflow separates three functions and links them through explicit records.

| Function | Implementation studied | Record needed to connect the work |
| --- | --- | --- |
| Scientific coordination and current accepted state | Notion Collaboration Log, numbered notebooks, and current-state pages | Purpose, governing decisions, assignments, evidence, review, and next action |
| Versioned artifacts | GitHub source, configuration, tests, manuscript files, commits, and pull requests | Exact repository revision and the change proposed for acceptance |
| Authoritative execution | User-controlled computing environment | Code version, command, inputs, configuration, environment, and outputs |

The shared record states why work was undertaken and what governs next; the repository identifies the source state; the execution record documents what was run. Large outputs may reside in a separate durable store linked from the same record. A Git commit identifies repository state, while a checksum computed after a file is complete identifies that file's bytes. Neither identifier establishes scientific correctness.

## Work contract and evidence

The current reusable contract organizes requirements under five stable identifiers: `USER-AUTHORITY`, `PRIOR-ART-LINEAGE`, `REFERENCE-VALIDATION`, `PRACTICE`, and `DURABLE-RECORD`. Together they define responsibilities, literature-search coverage, claim-specific citation checks, constructive artifact-based review, and recording duties. Adopters record project-specific choices and revisions rather than assuming that the supplied contract fits every project unchanged. The full directives and their precedence are given in Supplementary Note S1.

Evidence classes remain distinct. Model text is a proposal or interpretation. A platform sandbox run supports only the tested code and inputs in that environment. A repository commit establishes file identity, not validity. A final run is authoritative only for its recorded code, inputs, command, configuration, and environment. Acceptance requires evaluating that evidence against the task's stated criteria, not obtaining agreement between assistants.

The contract evolved during the work. Its current form includes later refinements, including separate review-request and approval fields and prospective session and exposure records. The retrospective evaluation below does not treat these refinements as controls present throughout the frozen corpus.
